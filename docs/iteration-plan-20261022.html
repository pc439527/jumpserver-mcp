一、结论先行

四份报告各自独立取证，结论高度收敛：连接器的内核（状态机 / 审计闭环 / 错误投影 / 资产不可达 STOP）已经成熟且经得起验证，剩余摩擦集中在四个接缝——跨目标导航、审批分类精度、输出体量、批量入参通道。

判断 1最高频缺陷是确定性代码缺陷，不是环境抖动。4 份报告独立记录同一现象（CRM「首次切换必失败」、泛微「命中率 100%」、ESB「最高频痛点」、采集「B1」）。根因在 src/jumpserver/session.ts:719 leave()——「发一次 exit + 等一次菜单回显」，失败即置 UNKNOWN 并把重试责任甩给调用方。 判断 2「假成功」比「失败」更危险，必须排在失败之前。CRM 症状 3：batch 返回 target=192.168.30.2 但 hostname=k8s-192-168-30-3，命令实际落在旧机器上却以成功状态返回——采集到错误主机的数据会一路带进报告结论。 判断 3有一半收益不在连接器内，在客户端。采集报告 A1：targets 数组被序列化坏，batch/compare/inspect/topology 四个工具全线报 must be array。连接器侧必须做降级入参兜底，但不能只靠连接器。 判断 4分类器放宽是安全边界变更，必须独立立项、独立验收。泛微报告明确建议：不宜与稳定性修复混在一起发布。fail-closed 是对的，错的是规则粒度。
总目标：把「日常可用性」问题清空——跨目标首调失败率 100% → ~0；只读命令审批拦截 → 0；输出入上下文量降一个量级。

实施中修正的两处计划偏差
  • A-1 根因比计划更深：不只是「重试不够」。KoKo exit 后只留裸提示符 [Host]>（无框线无编号行），而 looksLikeMenu() 要求框线+编号组合 ⇒ 成功的 leave 被判失败。修法：新增 waitForMenuReturn() 接受两种菜单形态，looksLikeMenuPrompt 作为可靠确认；looksLikeShellPrompt 导出用于「仍在资产 shell 内」判定（在 KoKo 菜单发 exit 会断开整个堡垒机会话，故重试有前置条件）。
  • A-2 判定比计划保守：不做「hostname 与请求名直接比对」，因为资产显示名 ≠ hostname 会造成大量误报。改为：请求目标是 IP 字面量 → 自身地址列表必须含它；hostname 内嵌 IP 与请求不符 → 明确 mismatch；其余一律 unverified（跳过而非失败）。用 hostname -I（A= 行）而非 ip -4 addr，无需 stripPrefixes 白名单。
  • A-7 连带改造：navigateToTarget() 返回 { session, status }（自愈会替换 session 对象，调用方持有的旧引用会指向死 PTY），3 个调用点（run / startJob / runTargetBatchGated）同步改。
风险：A-1/A-5 每次切换增加 2–3s/target（用 A-2 免重试路径对冲）；A-2 多网卡可能误报（先 20 台真实资产回归确定 stripPrefixes）；不可达目标绝不能进重试循环，否则又是一轮 2m53s。

B-1 实施偏差修正（2026-10-22，实施后回写）
  • 校验闸门在客户端，不在连接器。 宿主在发出 MCP 调用之前用 AJV 校验参数：app.asar.unpacked/cli/dist/codebuddy-lite-wb.mjs 偏移 5994979 附近 validateParams() → new Ajv({allErrors:true, coerceTypes:true})。coerceTypes:true 只启用 number 模式强转，不会把 string 变成 array；报错措辞 must be array 是 AJV 原生措辞（zod 会说 Expected array, received string），与 N-04 报告文案逐字吻合 ⇒ 失败发生在客户端，请求根本没发到服务端。
    ⇒ 推翻了「只加 z.preprocess、发布形态保持 array-only」的原设计：发布形态若是 array-only，客户端先拒，连接器内的归一就是死代码。发布形态必须是 anyOf: [{type:'array',…},{type:'string'}]——方向与原计划一致，但理由完全不同。
  • z.preprocess 必须在 union 之外，不能在 array 分支之内。若在分支内，string 会命中 union 的 z.string() 分支而永远走不到 array 分支，于是 min/max 边界对字符串形态完全失效——jumpserver_compare 要求 ≥2 个 target，而 "1.1.1.1"（1 个）会被放行 ⇒ fail-closed 违规。正确形态：z.preprocess(normalize, z.union([arrayWithBounds, z.string()]))。该缺陷由新增单测「the connector still normalizes the string into an array, and the bounds still apply」捕获。
  • 分隔符收紧：原计划写「逗号/空格」，实施改为空格不是分隔符（资产名可能含空格，如 "Web Server 01"），唯一例外是整段按空格切开后每段都是 IPv4 字面量。命令列表只按换行切分且不去重。
  • 额外加固：tasks 的 string 分支要求文本看起来像 JSON（以 [ 或 { 开头），否则 "not json" 会被放行并把垃圾交给 handler；profiles / stripPrefixes 也改为容错形态。
  • 预算影响：tools/list payload 23821 B → 24091 B（+270 B），上限 24500 B，单工具上限 1700 B，最大工具 jumpserver_inspect 1685 B。z.optional() 放在 union 外层（内层会发布 anyOf:[{not:{}},…]，每个 optional 字段多约 30 B）。
